Small enough to live on-chain.

        
A Solana transaction is at most 1,232 bytes. An ML-DSA-87 signature is almost four times that; a Falcon-512 signature fits with room to spare. That is why Solana's post-quantum work builds on Falcon.

      

      

        

        

          

            Signature schemes compared
            
              
SchemePublic keySignatureSecurity

            
            
              
Ed255193264Broken by a large quantum computer

              
Falcon-512897666NIST category 1

              
ML-DSA-872,5924,627NIST category 5, FIPS 204

            
          

        

        
Sizes in bytes. Category 1 is the level of AES-128; category 5 is AES-256. Vantax signs its own records with ML-DSA-87 and uses Falcon-512 where every byte is paid for.

      

    

  


  

    

      

        
Where Solana is with it.

      

      

        
Solana accounts still sign with Ed25519, and nothing here changes that. What changed in 2026 is that Falcon-512 became the post-quantum signature the ecosystem builds on.

        
Jump Crypto's proposal for verifying Falcon inside programs is SIMD-0416. Blueshift's Vector program already checks Falcon-512 signatures on-chain, for about 184,000 compute units each, and a Squads builder says he has used it on mainnet to let a Falcon key vote in a multisig.

        
The keys and signatures this page and vantax falcon make are standard Falcon-512 in the padded encoding those verifiers take: 897-byte public keys, 666-byte signatures, signed over the raw message. vantax falcon export prints the exact bytes.

        
Vantax isn't affiliated with Solana, Jump, Blueshift or Squads. Check any on-chain verifier's own documentation before you rely on it.

      

    

  


  

    

      

        
On your own machine.

        
The vantax command does the same with your operating system's randomness, and writes key files owner-only.

        
Install the CLI

      

      


# a key pair, plus a .pub.json to share
vantax falcon keygen -o hot.json

# sign a message, a file or hex bytes
vantax falcon sign -k hot.json -m "Built to be verified." -o hot.sig.json

# check it (exit code 1 if it doesn't verify)
vantax falcon verify -k hot.pub.json -s hot.sig.json -m "Built to be verified."

# the raw bytes, in base64 and hex, for on-chain verifiers
vantax falcon export -k hot.pub.json -s hot.sig.json

        
Files from the CLI open in the workbench above, and keys made in the browser sign with the CLI.

Questions.

      

        
Is my key sent anywhere?
No. Keys are made, used and checked inside this tab. The page makes no network requests for any of it, and nothing is stored once you close the tab.

        
Can I make my Solana wallet post-quantum with this?
Not on its own. A wallet's address is an Ed25519 key, and only a change to Solana itself can replace that. Today a Falcon key can authorise things through programs that verify Falcon-512 on-chain, and Vantax can bind a post-quantum key to your account and refuse actions that arrive without its signature.

        
Falcon-512 or ML-DSA-87?
Use ML-DSA-87 for keys that guard a lot and live off-chain: it is a published NIST standard at the highest security category. Use Falcon-512 where size matters, above all on-chain, where a 4,627-byte signature doesn't fit in a transaction.

        
Why does a new signature look different every time?
Falcon signs with fresh randomness each time, so two signatures over the same message differ. Both verify. Keys are the opposite: the same 48-byte seed always gives the same key.
